# リプライ元候補のグループ化に投稿時刻の近接条件を加える

## Why

リプライ元選択ドロップダウンで、`8/01 17:51` と表示されている投稿が 7/27 と 7/26 の間に並ぶ不具合がある。

`normalizeText` が URL を除去するため、Swarm チェックイン投稿は同じ場所に再訪するたび完全に同一の文字列になり、時期が離れていても 1 グループへ潰れる。そのうえで `MainContent.ts:167` が `grouped[key].postOfType[type] = post` と無条件代入しているため、各 SNS の投稿が新しい順に届く前提のもとで**より古い投稿が残る**。結果、表示日時とソートキーが別の投稿を参照する。

| | 参照するもの | 値 |
|---|---|---|
| `display_posted_at`（`MainContent.ts:162`） | グループ作成時＝最初＝最新の投稿 | `8/01 17:51` |
| `latestPostedAt`（`MainContent.ts:172-175`） | `postOfType` に残った＝上書き後＝最古の投稿 | 7/26 頃 |

これは本 capability の「各グループの並び順の基準にはグループ内の最新投稿日時を用いる」に違反した状態である。あわせて、同じ場所への過去のチェックインがグループへ吸収されて候補に現れず、リプライ元として選べない。

## What Changes

- グループ化の条件を「正規化テキストの一致」だけでなく「正規化テキストの一致 **かつ** 投稿時刻がグループ内のいずれかと 1 時間以内」とする
- グループの並び順の基準を、グループへ取り込んだ全投稿の最新日時とする（`postOfType` に残った投稿ではなく、取り込み時に記録した時刻を用いる）
- `frontend/src/lib/MainContent.ts` の `groupByText` 内を、本文キーごとに「グループ + 取り込んだ投稿時刻の一覧」を配列保持する形へ変更する

### 閾値を 1 時間とする根拠

同一内容の複数 SNS 同時投稿は `postToSns` が並行に実行するため、実際の投稿時刻の差は数秒〜数分にとどまる。1 時間の窓であれば、SNS 側の処理遅延やリトライを考慮しても同時投稿が分裂しない。一方、同じ場所への再訪や連投は必ず窓の外に出るため別グループになる。

キーに投稿日 (`YYYY-MM-DD`) を含める案も検討したが、23:59 と 00:01 に届いた同一投稿が分裂すること、同日に同じ本文を 2 回投稿すると同じ上書きが再発することの 2 点が残るため採用しない。

## Non-Goals

- `compareLength`（`MainContent.ts:153`）が全投稿の最短テキスト長に引きずられて 10 文字まで縮む問題。短いテスト投稿が 1 件あるだけで全体の比較精度が落ちるが、本 change では扱わない
- `posted_at` が不正値のときに `dayjs(...).valueOf()` が `NaN` となり、近接判定が常に偽になりソート順も不定になる問題。現行実装も同じ弱点を持ち、本変更で悪化しないため対処しない
- `PresentedPost` 型および `groupByText` の呼び出し側の変更
- グループ内に同一 SNS の投稿を複数保持して UI に並べる機能

## Impact

- **Affected specs**: PPP-004-reply-selection (変更)
- **Affected code**: `frontend/src/lib/MainContent.ts`（`groupByText` 内のみ。`latestPostedAt` ヘルパは削除）
- **Breaking changes**: なし。ドロップダウンの候補が増える方向の変更で、既存のリプライ投稿経路は変わらない
- **関連 Issue**: [#26](https://github.com/amay077/pppost/issues/26)
