# Spec Review: PPP-033-add-youtube-title-expansion

- Review date: 2026/08/04 19:33
- Reviewer: openspec-reviewer (claude)

## Overview

投稿本文中の YouTube URL（youtu.be 短縮 / youtube.com/watch / shorts）を特別処理し、`{タイトル} {展開後URL}` 形式へ本文全体を置換する提案。タイトル取得はキー不要の YouTube oEmbed API を新規 Netlify Function `youtube_oembed` で呼び出す。処理順は Swarm の次・一般的タイトル取得より優先。

- `openspec validate --strict` はパス済み（Change 'PPP-033-add-youtube-title-expansion' is valid）
- フォーマットは概ね規約適合: proposal セクション英語（Why / What Changes / Impact）、Requirement に SHALL あり、Scenario 見出しは英語+日本語併記、`#### Scenario:` 形式 × 6、ADDED 形式も正しい
- 既存パターン（Swarm 検出はフロント・スクレイピングはバックエンド、`fetch_title` の CORS/レスポンス形式）を踏襲しており、技術選定（oEmbed API・キー不要）は妥当
- 主な問題は spec のシナリオ網羅性不足（フル URL の正規化シナリオ欠落）と、既存「URL のみ判定」仕様との適用条件の曖昧さ

## Critical Issues

なし

## Major Issues

1. **フル URL（watch / shorts）の正規化シナリオが spec に存在しない**
   - design.md（Decisions の正規化ルール）は「`youtube.com/watch` → ホストを `www.youtube.com` に統一」「`youtube.com/shorts` → 形式維持でホストのみ統一」「フル URL でも `t=` のみ保持・`si=` 等は除去」と定義しているが、spec のシナリオは `Short URL expansion`（youtu.be → watch 展開）のみ。フル URL の検出シナリオ（`Full URL detection`）は検出までで、展開・パラメータ処理が検証できない。spec はアーカイブ時の正となりますため、フル URL の正規化（ホスト統一 + `t=` 保持 + トラッキングパラメータ除去）のシナリオを追加すべき。
2. **既存「URL のみ判定」仕様との適用条件の矛盾・曖昧さ**
   - 既存 spec `URL のみ判定` のシナリオ「URL 以外のテキストが含まれる → タイトル取得処理を実行しない・本文をそのまま使用する」に対し、本 delta の要件は「投稿本文中に含まれる YouTube URL」（= 周囲テキスト混在でも検出）と読める。design.md の Risks は「本文全体の置換により周囲のテキストが失われる → 実害なし」と認めており、混在テキストでも全体置換する意図と解釈できるが、spec のどこにも「周囲テキストがあっても置換する」または「URL のみテキストに限定する」の明示がない。`Priority over generic title fetch` も「URL のみの場合の一般的なタイトル取得処理をスキップ」と書くだけで、YouTube 処理自体の適用条件（URL のみ限定か否か）を定義していない。既存仕様との関係をシナリオで明確にすること。

## Minor Issues

1. **バックエンドの `url` 検証基準が曖昧**
   - tasks.md 1.1 の「`url` 未指定・不正な場合は 400」の「不正」の定義がない。設計上フロントが正規化済み URL を渡す前提だが、`youtube.com` / `youtu.be` ホストに限定する検証（oEmbed 誤用・SSRF 防止の観点）を明記すると実装が一意になる。既存 `fetch_title` は `isValidHttpUrl` のみだが、新規関数では厳格化を推奨。
2. **パラメータ除去の列挙が「`si=` など」に留まる**
   - design.md では `feature=` 等も除去対象。spec のシナリオを「`t=` 以外のクエリパラメータはすべて除去」と一般化して記述すると、実装の一意性と将来のパラメータ追加への頑健性が向上する。
3. **Requirement 名の表記が冗長**
   - 「YouTube URL の特別処理（YouTube URL の検出・整形）」は括弧内に要件名が重複する。シナリオ名と同様、シンプルな日本語名+英語名の併記（例: 「YouTube URL の特別処理（YouTube URL special handling）」）に整理すると可読性が上がる。
4. **shorts URL の出力形式シナリオ欠落（Major 1 の一部でもあるが個別にも）**
   - `youtube.com/shorts/<id>` は「形式は維持」と design.md にあるが、spec に shorts の展開後 URL 形式（`https://www.youtube.com/shorts/<video-id>` を維持するのか）のシナリオがない。Major 1 の修正時に併せて定義すること。

## Verdict

- 判定: FAIL
- 根拠: フォーマット・バリデーションは合格だが、Major 2 件がある。フル URL（watch/shorts）の正規化シナリオ欠落により spec 単体で実装の正解が確定せず（design.md にしか定義がない）、既存「URL のみ判定」仕様との適用条件（周囲テキスト混在時の全体置換の是非）の矛盾が解消されていない。レビューサイクルでシナリオ追加・明確化後、再レビューを推奨する。
