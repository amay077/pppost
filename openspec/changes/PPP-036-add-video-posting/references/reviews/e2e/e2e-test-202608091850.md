# E2E Test Report

## ステータス: PARTIAL（2 回目の実機テストで判明した問題を修正）

## 2 回目の実機テスト結果（2026-08-09 06:23 時点）と修正

### 3. Threads: 202 をフロントが成功扱いするバグ
- **事象**: バックエンドは `creation_id` を 202 で正しく返したが、フロントが「エラーと認識せず」（= 成功として表示）。最終化ポーリングは実行されず、コンテナは公開されない
- **原因**: `fetch` の `res.ok` は **202 Accepted でも true** を返す。`postToThreads` と `finalizeThreadsVideo` が `res.ok` を 202 判定より先にチェックしており、202 受信の瞬間に成功と判定されていた
- **修正**: 202 の判定を `res.ok` より先に移動（Threads・Bluesky の全投稿・最終化関数で統一）

### 4. Bluesky: 動画エンコードがポーリング予算（4 秒）内に完了しない
- **事象**: アップロード自体は成功（ジョブ開始）したが、`JOB_STATE_ENCODING` → `SCANNING` に時間がかかり `Video job not completed within budget`
- **原因**: Bluesky の動画エンコードは数十秒かかることがあり、同期 Function の 10 秒制限内では完了しない
- **修正**: Threads と同様に**非同期 2 段階投稿**へ変更
  - `bluesky_post` は動画を video.bsky.app へアップロードし、短時間ポーリング（3 秒）で完了しなければジョブ ID を **HTTP 202** で返す
  - 新設 `bluesky_video_finalize` がジョブの処理完了待ち（`getJobStatus`）→ `app.bsky.embed.video` での投稿を担当
  - フロントは 202 受信後、`bluesky_video_finalize` を 3 秒間隔で最大 60 秒ポーリング

### 5. Bluesky: 同一動画の再投稿で 409 already_exists
- **事象**: 同じ動画コンテンツの再投稿時に `uploadVideo` が 409 `already_exists` を返し失敗
- **原因**: 動画サービスは動画を**コンテンツハッシュで重複判定**する。処理済みの同一動画を再度アップロードすると 409 を返し、応答に処理済みジョブの `jobId`（`state: JOB_STATE_COMPLETED`）が含まれる
- **修正**: 409 時に応答の `jobId` で `getJobStatus` を呼び、処理済み動画の BlobRef を取得して同期投稿する。即時取得できない場合は 202 を返し `bluesky_video_finalize` に任せる

### 6. Misskey: 動画投稿が 30 秒タイムアウト → その後 drive/files が 403
- **事象 1**: `misskey_post` が 30000ms で打ち切られ失敗（Netlify 同期 Function の上限 30 秒）。`drive/files/create` の動画アップロードは Misskey 側の動画サムネイル生成（ffmpeg）を含むため 30 秒を超過
- **修正 1**: 非同期 2 段階化（`misskey_post` は 202 + `video_url` を返し、クライアントが `misskey_video_finalize` をポーリング）
- **事象 2**: 初期の finalize 実装は `drive/files/upload-from-url` で取り込んだ後、`drive/files` でファイルを検索しようとしたが、**403 PERMISSION_DENIED**（`drive/files` は `read:drive` 権限が必要。アプリの MiAuth は `write:notes,write:drive,read:account` のみ）
- **修正 2**: 検索 API を廃止し、finalize で **`drive/files/create`（`write:drive` = 画像投稿と同じ権限で動作）** に変更。R2 から動画を取得 → drive アップロード → `notes/create`。再接続不要
  - 補足: タイムアウト後に再試行された場合、`drive/files/create` は同一ハッシュの既存ファイルを返すため収束する

## 本番での実機エラーと修正（2026-08-09）

### 1. Bluesky: 501 MethodNotImplemented（`app.bsky.video.uploadVideo`）
- **事象**: `bluesky_post.js` が PDS（bsky.social）へ `app.bsky.video.uploadVideo` を呼び出し、`MethodNotImplemented`（501）で失敗
- **原因**: 動画エンドポイントは PDS ではなく**動画サービス（video.bsky.app）**が提供する。公式ドキュメント（Recommended method）では、`com.atproto.server.getServiceAuth` でサービス トークンを発行し、`video.bsky.app/xrpc/app.bsky.video.uploadVideo?did=...&name=...` へ直接アップロードし、状態確認も `video.bsky.app` の `getJobStatus` に対して行う
- **修正**: 公式ドキュメントに従い、サービス トークン発行 → video.bsky.app へのアップロード → video.bsky.app でのポーリングに変更。`already_exists`（処理済み動画の再アップロード）時は生応答から BlobRef を取得するフォールバックも追加

### 2. Threads: `threads container not ready within budget`
- **事象**: 動画コンテナが Netlify 同期 Function の実行時間予算（8.5 秒）内に `FINISHED` にならず投稿失敗
- **原因**: Threads の動画コンテナ処理は Meta 側で数十秒かかることがあり、同期処理では完了できない
- **修正**: **非同期 2 段階投稿に変更**
  - `threads_post` は動画コンテナを作成し、予算内に `FINISHED` にならない場合は `creation_id` を **HTTP 202** で返す（失敗にしない）
  - 新設 `threads_video_finalize` がコンテナの `FINISHED` 待ち → 公開（4279009 時はコンテナ再作成リトライ）→ PR ゴースト投稿を担当
  - フロントは 202 受信後、`threads_video_finalize` を 3 秒間隔で最大 60 秒ポーリング
  - Threads 共通ロジックは `backend/netlify/lib/threads.js` に抽出
