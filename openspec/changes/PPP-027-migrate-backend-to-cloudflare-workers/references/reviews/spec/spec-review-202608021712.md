## Major Issues

### Issue 1: `threads_post` の実行時間予算定数を Workers 向けに再導出するタスクが無く、新設シナリオ「上限枚数のカルーセル投稿が完了する」が達成不能

- **Severity**: Major
- **Location**: `tasks.md`（3.1、5.4）/ `specs/backend-hosting/spec.md`（L56-60）/ `specs/threads-posting/spec.md`（L13）/ `design.md`（Decisions 全般）
- **Line**: `tasks.md` L27、L48
- **Description**:
  PPP-028 で `backend/netlify/functions/threads_post.js` に実行時間予算が実装済みであり、定数は Netlify の壁時計 10 秒制限から逆算されている:

  ```js
  const OVERALL_BUDGET_MS = 8500;
  const CHILD_WAIT_BUDGET_MS = 5000;
  const GHOST_MIN_BUDGET_MS = 2000;
  // L56: deadline は絶対時刻（ミリ秒）。Netlify 同期 Function の実行時間制限に収めるため有限に打ち切る。
  ```

  本 change は次の 2 つを新たに規定した:

  - `threads-posting` デルタ L13: 「予算の値は実行基盤の制約（壁時計上限、CPU 時間上限、エッジの応答開始タイムアウト等）から導き、実行基盤に依存しない仕様として特定のホスティングサービス名や秒数を固定してはならない (SHALL NOT)」
  - `backend-hosting` L56-60 Scenario「上限枚数のカルーセル投稿が完了する」: 画像 10 枚の Threads 投稿で「実行基盤の実行時間の上限によるタイムアウトは発生せず、投稿が完了する」

  ところが `tasks.md` には予算定数に触れるタスクが 1 つも無く（`grep` で `予算` / `BUDGET` / `8500` は proposal L33 の #28 参照 1 件のみ）、`threads_post` は 3.1 で「**機械的ルート移植（fetch / FormData 置換のみ）**」に分類されている。このまま実装すると:

  1. `OVERALL_BUDGET_MS = 8500` が Workers へそのまま持ち込まれ、10 枚のカルーセルは子コンテナ待ちの途中（`CHILD_WAIT_BUDGET_MS = 5000` 到達時）に `waitForContainerReady` が false を返し、**投稿が失敗として扱われる**。`backend-hosting` の新設シナリオは満たせない。
  2. 移行ゲート 5.4「Threads へ画像 10 枚を投稿し、応答開始までの総所要時間がエッジのタイムアウト（約 100 秒）に対して余裕があることを記録する」も、8,500 ms で打ち切られるため測定自体が成立しない。
  3. `threads_post.js` L56 のコメント「Netlify 同期 Function の実行時間制限に収めるため」が残り、`threads-posting` デルタの「特定のホスティングサービス名を固定してはならない (SHALL NOT)」に反する状態がコード側に残存する。

  これは Iteration 1 の Issue 1（threads-posting デルタの追加）と Issue 6（上限枚数シナリオの追加）を修正したことで**新たに顕在化した Spec ↔ Tasks の欠落**である。
- **Suggestion**:
  1. `tasks.md` 3.1 から `threads_post` を切り出し、4 章（書き換えを伴うルート移植）へ移す。例: 「4.x `threads_post` の実行時間予算定数（`OVERALL_BUDGET_MS` / `CHILD_WAIT_BUDGET_MS` / `GHOST_MIN_BUDGET_MS`）を Workers の制約（エッジの応答開始タイムアウト約 100 秒）から再導出して更新し、`waitForContainerReady` のコメントから `Netlify 同期 Function` の記述を除去する」
  2. `design.md` に決定を 1 件追加する（例: D12「実行時間予算の再導出」）。Workers 側の予算値と、その根拠（エッジタイムアウト 100 秒に対する安全率、子コンテナ待ちと PR ゴーストへの配分）を明記する。`threads-posting` デルタが「実行基盤の制約から導く」と定めた以上、導出結果は設計文書に残す必要がある。
  3. 移行ゲート 5.4 に「再導出後の予算値で 10 枚カルーセルが成功すること」を合格条件として明示する。

## Minor Issues

### Issue 2: `threads-posting` デルタが PPP-028 の「コンテナの完了待ちを予算内に収める」SHALL を落としている

- **Severity**: Minor
- **Location**: `specs/threads-posting/spec.md`（L13）
- **Description**: PPP-028 適用後の本文は「…実行時間予算を定め、**コンテナの完了待ちをその予算内に収めなければならない (SHALL)**」だが、本デルタは「…実行時間予算を定め、**ポーリングの間隔と回数を有限に制限しなければならない (SHALL)**」へ置換している。基盤名・秒数の除去（Iteration 1 Issue 1 の趣旨）に必要な変更は「Netlify 同期 Function の実行時間制限」の部分のみであり、後半の規範文まで差し替える必然性が無い。`openspec/AGENTS.md` L302・L305 が警告する「MODIFIED で前の記述を落とす」ケースに該当する。実害は小さい（「予算内に `FINISHED` にならない場合は失敗として扱う」が残るため強制力は保たれる）が、archive 時に PPP-028 の成果の一部が消える。
- **Suggestion**: 「…実行時間予算を定め、コンテナの完了待ちをその予算内に収めなければならない (SHALL)。ポーリングの間隔と回数は有限に制限しなければならない (SHALL)。」のように両方を残す。

### Issue 3: `backend-hosting` が参照する「Misskey・Bluesky の添付上限枚数」が既存 spec に存在しない

- **Severity**: Minor
- **Location**: `specs/backend-hosting/spec.md`（L48）
- **Description**: 「各 SNS の capability が定める添付上限枚数（Threads は 10 枚、**Misskey・Bluesky は各 capability の規定**）」とあるが、`openspec/specs/misskey-posting/spec.md` に添付枚数の上限規定は無く（規定があるのはファイルサイズ 500 MB とリサイズ不適用のみ）、Bluesky は **capability 自体が存在しない**（PPP-029 proposal L48 も「Bluesky の画像縮小処理は現状どの capability にも規定がない」と認めている）。参照先が無いため、Misskey・Bluesky については何枚で検証すれば要件充足かが依然として決まらない。Threads の 10 枚とシナリオ 2 本により最悪ケースの検証可能性は確保されているため Minor とする。
- **Suggestion**: 「Threads は 10 枚（`threads-posting` capability の規定）、Misskey・Bluesky は本アプリが扱う最大枚数（現行 UI の制限に従う）」のように、参照ではなく本 spec 内で閉じた表現へ改める。または Misskey・Bluesky を列挙から外し、Threads の 10 枚を最悪ケースとして代表させる。

### Issue 4: proposal のデプロイ用トークンの記述が design D11 と食い違う

- **Severity**: Minor
- **Location**: `proposal.md`（L8）/ `design.md`（D11: L103）
- **Description**: proposal L8 は「ランタイムから `CF_API_TOKEN` という秘密情報が不要になる（**デプロイ時のみ Workers スコープのトークンを使う**）」と断定しているが、design D11 の「射程の明確化」は「手動運用では開発者ローカルの `wrangler login`（OAuth）で足り、**アカウント全体に効くトークンをどこにも常設しない**。CI 化する場合は `Workers Scripts:Edit` にスコープしたトークンを GitHub Secrets へ置く」としている。D11 で手動デプロイを採用した以上、「デプロイ時のみトークンを使う」は現時点では成立しない（CI 化した場合の話である）。
- **Suggestion**: proposal L8 を「…不要になる（デプロイには Cloudflare の認証が別途必要だが、手動運用では `wrangler login` の OAuth で足り、常設トークンは不要。CI 化する場合のみ Workers スコープのトークンを GitHub Secrets へ置く。D11）」へ修正する。

### Issue 5: `credential-custody` デルタの追記文に規範動詞が無い

- **Severity**: Minor
- **Location**: `specs/credential-custody/spec.md`（L7）
- **Description**: 追記された「D1 へのアクセスは実行基盤のバインディングで行い、その方式は `backend-hosting` capability の規定に従う。」は規範的な内容にもかかわらず SHALL / MUST を伴わない平叙文である。`openspec/AGENTS.md` L289「Use SHALL/MUST for normative requirements」に照らすと弱い。要件全体には他に SHALL があるため validate は通るが、この文だけを根拠に違反判定ができない。
- **Suggestion**: 「D1 へのアクセスは実行基盤のバインディングで行わなければならず (SHALL)、その方式は `backend-hosting` capability の規定に従う。」へ改める。

### Issue 6: アーカイブ順序の前提（#28 / #29 の先行アーカイブ）を確認するタスクが無い

- **Severity**: Minor
- **Location**: `proposal.md`（L28-35）/ `tasks.md`（7 章・8 章）
- **Description**: proposal は「本 change の spec デルタは #28 / #29 が**先にアーカイブされること**を前提に記述している」「いずれかが先にアーカイブされなかった場合は、本 change のアーカイブ前にデルタのベース本文を取り直す」と明記しており、方針としては妥当である（実際、PPP-028 の残タスク 5.2・5.8 は `netlify dev` と Netlify Function ログ前提のため Netlify 稼働中に完了する必要があり、順序に無理は無い）。しかし tasks.md にこの前提を確認する作業が無く、archive 時に人手の記憶頼りになる。
- **Suggestion**: 8 章の末尾に「8.3 archive 前に `openspec list` で PPP-028 / PPP-029 がアーカイブ済みであることを確認する。未アーカイブの場合は `specs/threads-posting/spec.md` および `specs/credential-custody/spec.md` のベース本文を `openspec/specs/` の現行本文から取り直す」を追加する。
