### Issue 1: `threads-posting` spec が「Netlify Function の既定 10 秒タイムアウト」を SHALL の根拠にしており、移行後に虚偽になるが MODIFIED デルタが無い

- **Severity**: Major
- **Location**: `proposal.md`（L5、L33）/ 既存 `openspec/specs/threads-posting/spec.md`（L54）
- **Description**: 既存 spec に「バックエンドの実行時間制約（**Netlify Function の既定 10 秒タイムアウト**）に収まるよう、ポーリングの間隔と回数は有限に制限しなければならない (SHALL)」という要件が存在する。本 change は実行基盤ごと差し替えるため、この SHALL の根拠（Netlify・10 秒）は移行完了時点で成立しなくなる。しかし `## Impact` の Affected specs は `backend-hosting (新規)` のみで、`threads-posting` の MODIFIED デルタが無い。結果として、アーカイブ後の `openspec/specs/` に「Netlify Function の既定 10 秒」という誤った制約が残り、新しい backend-hosting 要件（CPU 時間ベース）と正面から矛盾する。
  さらに数値そのものが 3 者でバラバラである: 既存 spec は「10 秒」、本 proposal は「壁時計 30 秒」（L5）、実コードのコメント（`backend/netlify/functions/misskey_post.js:64-65`）も「30 秒」。Netlify Functions の同期実行の公称上限は既定 10 秒・引き上げ時 26 秒で、`backend/netlify.toml` にタイムアウト設定は無い。「30 秒」の出典が不明なまま Why の一次根拠になっている。
- **Suggestion**: (1) `specs/threads-posting/spec.md` に MODIFIED デルタを追加し、当該要件から基盤名・秒数の直書きを外す（例:「バックエンドの実行時間制約に収まるよう、ポーリングの間隔と回数は有限に制限しなければならない (SHALL)」）。既存要件は全文コピーのうえ差分を適用すること。(2) proposal の「壁時計 30 秒」を #25 の実測値または Netlify の公称値（10 秒 / 引き上げ時 26 秒）に置き換え、出典を明記する。

### Issue 2: `credential-custody` の「Cloudflare の認証情報はサーバー側（環境変数）にのみ置き」がバインディング化と整合しないのに MODIFIED デルタが無い

- **Severity**: Major
- **Location**: `proposal.md`（L33）/ `specs/backend-hosting/spec.md`（L48）/ 既存 `openspec/specs/credential-custody/spec.md`（L31）
- **Description**: 既存 `credential-custody` は「保管に用いる鍵・**Cloudflare の認証情報**はサーバー側（環境変数）にのみ置き、クライアントへ渡してはならない」と定めている。本 change 後は D1 アクセスに Cloudflare の認証情報自体が存在せず（バインディング）、`CF_API_TOKEN` の保持は新 spec で明示的に禁止される。つまり既存要件の前提（Cloudflare 認証情報が環境変数に存在する）が失効する。禁止方向の強化なので実害ある矛盾ではないが、アーカイブ後に「環境変数に置く Cloudflare 認証情報」という存在しない前提が spec に残る。加えて、`credential-custody` は「Cloudflare D1 に AES で暗号化して保存」というアクセス手段非依存の書き方をしている一方、新 `backend-hosting` は D1 バインディング必須を SHALL 化するため、どちらが権威かが読み手に判別できない。
- **Suggestion**: `specs/credential-custody/spec.md` に MODIFIED デルタを追加し、L31 を「保管に用いる鍵は Workers の secrets（サーバー側）にのみ置き…」等へ改め、D1 へのアクセス方式は `backend-hosting` を参照する旨を明記する。または proposal の Impact に「`credential-custody` は文言のみ更新」と記載したうえでデルタを追加する。

### Issue 3: Workers の env アクセスモデルが未定義で、「`query(sql, params)` シグネチャ維持」「`token-store.js` / `pr-ghost.js` は無改変」という設計の前提が成立していない

- **Severity**: Major
- **Location**: `design.md`（D2: L32-36、D3: L38-42）/ `tasks.md`（1.2、2.1、2.2、2.3）
- **Description**: Netlify Functions は `process.env` がグローバルに使えるが、Workers ではバインディング・secrets はリクエストごとの `env` オブジェクト（Hono では `c.env`）で渡る。実コードは次の依存を持つ:
  - `backend/netlify/lib/d1.js` — `process.env.CF_*` を参照。バインディング化すると `env.DB` を関数へ届ける必要があり、`query(sql, params)` の 2 引数を保ったままでは呼び出し側（`token-store.js` / `pr-ghost.js`）へ env を渡す経路が無い。
  - `backend/netlify/lib/crypto.js` — `getKey()` が `process.env.PPPOST_DATA_SECRET` を直接読む。`token-store.js` は `encrypt` / `decrypt` を引数なしで呼ぶ。
  D2 は「`token-store.js` と `pr-ghost.js` は `query()` だけに依存しており呼び出し側は無改変」と断言し、D3 も「鍵導出は不変」（tasks 2.2）としているが、env の届け方（`c.env` を引数で伝播する / モジュールスコープにリクエスト毎に束縛する / `nodejs_compat` の `process.env` ポリフィルに依存する）を決めない限り、この結論は導けない。特に `process.env` へのバインディング流し込みは `compatibility_date` 依存の機能であり、tasks 1.2 に `compatibility_date` の指定タスクが無い（`nodejs_compat` フラグのみ）ため、D3 の移行ゲート（2.4 の復号検証）が何を検証したことになるかも曖昧になる。
- **Suggestion**: design に「D9: env / secrets の受け渡し方式」を追加し、(a) `c.env` を明示的に引数で渡す（`query(env, sql, params)`・`encrypt(secret, plaintext)` へシグネチャ変更＝`token-store.js` / `pr-ghost.js` も改変対象）か、(b) `nodejs_compat` + 所定の `compatibility_date` による `process.env` 参照を採るかを決定し、採用理由と副作用（(b) の場合は compat date 固定が前提になること）を記す。tasks 1.2 に `compatibility_date` の明示、2.1〜2.3 に選択した方式に沿った改変範囲を反映すること。D2 の「無改変」記述も実態に合わせて修正する。

### Issue 4: `bluesky_post.js` の自己サブリクエスト（`process.env.URL` + `/.netlify/functions/...`）が design/tasks から欠落している

- **Severity**: Major
- **Location**: `tasks.md`（3.4、3.5、4.2）/ `design.md`（Decisions 全般）
- **Description**: `backend/netlify/functions/bluesky_post.js` は OGP 取得とサムネイル取得で、自分自身のサイトの別関数を HTTP で呼んでいる:
  - L261: `${process.env.URL || 'http://localhost:9000'}/.netlify/functions/cors_proxy?url=...`
  - L297: `${process.env.URL || 'http://localhost:9000'}/.netlify/functions/fetch_image?url=...`
  ここには (1) Netlify が自動注入する `URL` 環境変数、(2) `/.netlify/functions` という Netlify 固有パス、(3) 自 Worker への自己サブリクエスト（Cloudflare では自分自身のルートへの fetch はループ扱いとなり得るため、通常はハンドラ直接呼び出しへ置き換える）という 3 つの Netlify 依存が同時に存在する。tasks 4.2 は `bluesky_post` について「`resizeImageIfNeeded` の photon 化」しか挙げておらず、3.4（cors_proxy / fetch_image の移植）も呼び出し側の書き換えに触れていない。このまま実装すると Bluesky のリンクカード（OGP 画像・YouTube サムネ）が無言で欠落する（本文の `try/catch` で握り潰され、投稿自体は成功する＝検知しづらい退行）。
- **Suggestion**: tasks 4.2 に「`bluesky_post` の OGP 取得・画像取得を、`cors_proxy` / `fetch_image` の処理関数を直接呼び出す形へ書き換える（`process.env.URL` と `/.netlify/functions` パスの除去）」を追加し、design に共有ロジックの切り出し方針（`src/lib/` へ関数化して両ルートから使う等）を 1 決定として記載する。あわせて Phase 1 の検証に「Bluesky へ URL 付き投稿を行い、リンクカードにサムネイルが表示されること」を追加する。

### Issue 5: Worker のデプロイ手段（CI/CD）が未決定・未タスク化で、現行の自動デプロイが失われる

- **Severity**: Major

- **Description**: 現在バックエンドは Netlify の GitHub 連携で `main` への push により自動デプロイされる（`README.md` L190、L198-202）。本 change の tasks は `wrangler deploy` の手動実行（5.1）と README 更新（8.1）しか持たず、移行後のデプロイ方式（手動運用にするのか、GitHub Actions へ `wrangler-action` を追加するのか）が design にも tasks にも無い。Phase 3 で Netlify を廃止した時点で、バックエンドの継続的デプロイが定義されないまま消える。加えて、CI からデプロイする場合は Workers スコープの Cloudflare API トークンを GitHub Secrets へ置くことになり、proposal の「`CF_API_TOKEN` という秘密情報自体が不要になる」（L7）という主張の射程（＝ランタイムのアカウント全体権限トークンは不要になるが、デプロイ用トークンは別途必要）を明確にする必要がある。D8 のビルド時刻 vars 注入（`--var` を誰がいつ渡すか）も、この決定が無いと確定しない。

### Issue 6: Requirement「画像投稿が壁時計制限で失敗しない」の「対応上限枚数」が未定義でテスト不能

- **Severity**: Major
- **Location**: `specs/backend-hosting/spec.md`（L36-44）
- **Description**: 要件本文は「**対応上限枚数**までの画像付き投稿を…失敗させてはならない (SHALL NOT)」だが、本 spec 内に上限枚数の定義がなく、他 spec では SNS ごとに異なる（`threads-posting` は最大 10 枚、Misskey・Bluesky は別条件）。何枚で検証すれば要件を満たしたと言えるかが決まらない。シナリオも「Misskey へ画像 3 枚」の 1 本のみで、最悪ケース（Threads 10 枚のカルーセル、1 枚あたり約 10 秒の処理）を担保していない。移行の一次動機がまさにこの制限であるため、受け入れ基準の曖昧さは致命的である。

### Issue 7: R2 クレデンシャルの「対象バケットにスコープ」SHALL に対応するタスクが無い

### Issue 8: CORS（クロスオリジン許可）が spec の要件になっていない

- **Severity**: Major
- **Location**: `specs/backend-hosting/spec.md`（Requirements 全般）/ `proposal.md`（L12）/ `tasks.md`（1.4）
- **Description**: フロントは GitHub Pages（別オリジン）から API を呼ぶため、CORS 応答はエンドポイント互換性の一部として必須の振る舞いである。現行は各関数の CORS ヘッダに加え、`backend/netlify.toml` の `[[headers]] Access-Control-Allow-Origin = "*"` というプラットフォーム設定にも支えられており、Workers ではこのプラットフォーム側の保険が消える。proposal は「CORS プリアンブルをミドルウェアへ集約する」（L12）と意図を述べ、tasks 1.4 も作業を持つが、spec には CORS に関する要件・シナリオが 1 つも無い。「proposal の意図が spec の要件として明文化されていない」典型で、`OPTIONS` プリフライトや `Authorization` ヘッダ許可が欠けても spec 上は違反にならない。

### Issue 9: ロールバックのシナリオに対応する検証タスクが無い

### Issue 10: 移行ゲート 5.3 の合格基準が「余裕があること」で数値が無く、判定不能

- **Severity**: Major
- **Location**: `tasks.md`（5.3）/ `design.md`（Risks: L76）
- **Description**: 「8 MB 級画像で photon リサイズの CPU 時間を実測し、**上限に対して余裕があること**を記録する」は、合格・不合格の境界が定義されていない。design 側も「Paid の 30 秒に収まらない事態は考えにくい」と定性的で、ゲートとして機能しない。同種の曖昧さは 7.1「1〜2 週間の**安定稼働**を確認する」にもあり、何をもって安定とするか（エラー率、失敗投稿ゼロ等）が定義されていない。

### Issue 11: Cloudflare 側にも応答開始のタイムアウトがあるため「壁時計制限が消える」は厳密には不正確

- **Severity**: Minor
- **Location**: `proposal.md`（L7）/ `design.md`（Goals: L15）
- **Description**: Workers に CPU 時間ベースの制限しか無いのは正しいが、Cloudflare のエッジは応答ヘッダが一定時間（一般に約 100 秒）返らない接続を打ち切る。「壁時計制限が消える」と言い切ると、Issue 6 で指摘した最悪ケース（10 枚 × 約 10 秒）の評価が甘くなる。
