## Summary

## Major Issues

### Issue 1: 「ノート ID の直接入力」の SHALL が既存 `getPostId` では満たせず、全 SNS の投稿が無言で中断する

- **Severity**: Major
- **Location**: `specs/misskey-posting/spec.md`（L176）/ `tasks.md`（3.7）/ `design.md`（D8）
- **Description**: spec は「リプライ元選択ドロップダウンで選択された自投稿からの導出と、ユーザーがノート URL **またはノート ID** を直接入力する手動指定の双方を受け付けなければならない (SHALL)」と規定している。しかし tasks 3.7 / design D8 が再利用を指示する `MainContent.svelte:307-315` の `getPostId` は `new URL(url)` を無条件に呼ぶため、`abcdefg` のような裸のノート ID を渡すと `TypeError: Invalid URL` を送出する。この例外は `post()` の `catch (error) {}`（`MainContent.svelte:346-348`、本体が空）で握り潰され、**Misskey だけでなく Mastodon・Bluesky・Threads を含む投稿処理全体が、ユーザーへの通知なしに中断する**。つまり spec の SHALL は満たされず、かつ既存 SNS の動作にも影響が出る（proposal の「既存動作を一切変えない」に反する）。
- **Suggestion**: 次のいずれかを選ぶ。(a) tasks に「`getPostId` を URL としてパースできない入力はそのまま ID として返すよう修正する」タスクを追加し、`design.md` D8 を更新する（Mastodon・Bluesky の同一の潜在バグも同時に解消される）。(b) spec を「ノート URL の手動入力を受け付けなければならない」に限定し、ID 直接入力を Non-Goals に移す。いずれの場合も、対応するシナリオ（`#### Scenario: ノート ID を手動入力してリプライする`）と検証タスクを追加すること。

### Issue 2: 「グループに Misskey の投稿が含まれない場合は `replyId` を付与しない」が tasks 3.7 のフォールバックと矛盾する

- **Severity**: Major
- **Location**: `specs/misskey-posting/spec.md`（L178）/ `tasks.md`（3.7）
- **Description**: spec は「リプライ元が選択されておらず、かつ手動指定もない場合、**または選択されたリプライ元グループに Misskey の投稿が含まれない場合**、システムは `replyId` を付与せず通常投稿として処理しなければならない (SHALL)」と規定する。一方 tasks 3.7 が指示する式は `getPostId(replyToPost?.postOfType['misskey']?.url ?? replyToIdForMisskey)` であり、グループに Misskey 投稿が無い場合は手動入力欄の値へフォールバックする。手動入力欄はグループ選択時に非表示になるだけでクリアされない（`MainContent.svelte:459-460` を見る限り、クリアは投稿成功時と Clear ボタン時のみ）ため、「手動入力 → グループ選択」の順に操作すると、spec が禁じたはずの `replyId` が付与される。
- **Suggestion**: spec 側の条件を実装意図に合わせて「リプライ元グループにも手動入力欄にも Misskey のノート指定がない場合」と書き換える。あるいは tasks 側でグループ選択時に `replyToIdForMisskey` をクリアするタスクを追加する。

### Issue 3: `withReplies: false` により Misskey だけリプライ元候補の母集合が他 SNS と食い違う

- **Severity**: Major
- **Location**: `specs/misskey-posting/spec.md`（L140）/ `tasks.md`（8.3）/ `design.md`（D6 周辺に判断の記載なし）
- **Description**: spec は「リプライ元候補として不適切であるため、システムはリノート（`withRenotes`）とリプライ（`withReplies`）を取得対象に含めてはならない (SHALL NOT)」としている。しかし既存 SNS では、Mastodon は `/api/v1/accounts/{id}/statuses`（`exclude_replies` 未指定＝リプライを含む、`mastodon_posts.js:51`）、Bluesky は `agent.getAuthorFeed`（既定 `posts_with_replies`、`bluesky_posts.js:66`）でいずれも自分のリプライを候補に含めている。Misskey だけ除外すると、(1) スレッドの 2 通目以降に連ねる運用ができない、(2) クロス投稿されたリプライが `PPP-004-reply-selection` のグループ化で「Mastodon/Bluesky にはあるが Misskey には無いグループ」となり、同じグループを選んでも Misskey だけ通常投稿になる、という機能差が生じる。これは MODIFIED した `PPP-004-reply-selection` の「グループ化の対象は現在対応しているすべての投稿先 SNS」の意図とも整合しない。リノート除外には合理性があるが、リプライ除外には根拠が示されていない。
- **Suggestion**: `withReplies: true`（リノートのみ除外）へ改めるか、リプライを除外する明確な理由と上記トレードオフを `design.md` の Decision として追記し、spec にも「他 SNS と候補集合が異なりうる」旨を明記する。

### Issue 4: ホスト検証要件が文字列形式検証では達成できない（検証不能な受け入れ条件）

- **Severity**: Major
- **Location**: `specs/misskey-posting/spec.md`（L45）/ `tasks.md`（5.2）
- **Description**: spec は「英数字・ハイフン・ドットからなる公開ドメイン形式であることを確認し、`localhost`、IP アドレスリテラル、**およびプライベート・ループバック・リンクローカルのアドレスを拒否しなければならない** (SHALL)」と規定するが、tasks 5.2 は文字列形式の検証しか指示していない。`localtest.me`（→ 127.0.0.1）のように、公開ドメイン形式でありながら内部アドレスへ解決される名前は素通りするため、この SHALL は実装手段と一致せず、そのままでは達成の可否を判定できない。design.md D3 も「ホスト名は公開ドメイン形式に限定」としか述べておらず、名前解決結果の扱いが未定義。
- **Suggestion**: 要件の射程を「IP アドレスリテラル（ループバック・プライベート・リンクローカルを含む）と `localhost` を拒否する」に限定して文字列検証で達成可能にするか、名前解決後のアドレス判定を行う旨をタスク・design に明記する。前者を採る場合は「DNS 解決結果までは検証しない」ことを Risks / Trade-offs に残すこと。

### Issue 5: `sns-posting` の `## Purpose` が更新されず、archive 後に spec 内で自己矛盾する

- **Severity**: Major
- **Location**: `specs/sns-posting/spec.md`（delta）/ `openspec/specs/sns-posting/spec.md:4` / `tasks.md`
- **Description**: 既存 spec の Purpose は「投稿対象は Mastodon と Bluesky とし、Twitter (X) はフロントエンドから廃除する」であり、本 change の MODIFIED 要件（Mastodon・Bluesky・Threads・Misskey に限定）と真っ向から矛盾する。OpenSpec の archive 実装は `## Requirements` セクションのみを差し替え、その前の本文（タイトル・Purpose）を原文のまま保持する（`archive.js` の `extractRequirementsSection` の `before` を再利用）ため、archive しても Purpose は自動更新されない。tasks.md にも更新タスクがない。
- **Suggestion**: tasks.md の「10. ドキュメント」に「archive 時に `openspec/specs/sns-posting/spec.md` の Purpose を 4 SNS 対応へ書き換える」タスクを追加する（proposal の What Changes にも一文を追記するとより明確）。

### Issue 6: spec のシナリオに対する検証タスクが複数欠落している

- **Severity**: Major
- **Location**: `tasks.md`（11. 動作検証）
- **Description**: 検証セクション自体は充実しているが、spec で SHALL として定義した以下のシナリオに対応する検証項目がない。
  - `Scenario: 画像アップロードに失敗する` → 「ノートが作成されない」ことの確認（部分投稿が残らないことは本要件の肝）
  - `Scenario: Misskey の取得失敗は他 SNS に影響しない` → ローディング解除と他 SNS 候補の表示確認
  - `Scenario: 上限を超える本文` → 3000 文字超で Misskey のみ失敗し、エラー一覧に `Misskey` が出ること
  - `Scenario: 別のインスタンスに接続する` → `misskey.io` 以外のホストで環境変数変更なしに接続できること
  - `Scenario: テキストのみ投稿する` → `fileIds` を送らないこと（tasks 7.7 の「空配列を送らない」の裏取り）
- **Suggestion**: 上記 5 点を `11.x` に追加する。少なくとも「画像アップロード失敗時にノートが作られない」「上限超過時に Misskey のみ失敗」は手動で再現可能なので必須とする。
